# 0004. Share the launch app's Neon database

Status: accepted (2026-11-13)

## Context

The restaurant launch app has 26 tables (tasks, vendors, menu_items, inventory_items, invoices and others). The owner wants the command center to use the same database, so both apps work on one set of data. The database is the `production` branch of the Neon project "Launch app".

The launch tables follow their own conventions, which differ from ADR 0002:

- ids are `BIGINT GENERATED BY DEFAULT AS IDENTITY`, not UUIDs;
- many columns are camelCase and must be quoted in SQL (`"assignedTo"`, `"isCritical"`, `"linkedTaskId"`, `"totalCost"`);
- lists and objects are JSONB (`tasks.checklist`, `task_todos.subtasks`, `notes.files`);
- money and quantities are NUMERIC.

## Decision

`DATABASE_URL` points at that `production` branch. Integration tests use a separate branch copied from it, `command-center-test`. The command center adds its own tables beside the launch tables and never changes the launch tables.

- The command center owns only `organizations`, `locations`, `employees`, `roles`, `role_permissions`, `role_assignments`, `invitations` and `audit_log` (listed in `drizzle.config.ts` as `APP_OWNED_TABLES`). Its migrations create only these, its types and its functions.
- `drizzle.config.ts` limits drizzle-kit to those tables (`tablesFilter`) and refuses `drizzle-kit push`, which would otherwise offer to drop the launch tables. Schema changes go through `db:generate` and `db:migrate` only.
- Launch tables are never dropped, truncated, renamed or re-created, and no migration may alter them without explicit owner approval.
- When a feature needs a launch table, it is described in Drizzle exactly as it exists (BIGINT ids, quoted camelCase names, JSONB, NUMERIC). Those descriptions are kept out of the migration schema so drizzle-kit never generates SQL for them. NUMERIC and BIGINT values are converted to JavaScript numbers when read.
- New command-center features (orders, shifts and so on) get new tables, after owner approval.
- Neon Auth stays in the original Neon project. Its `neon_auth` tables live in that project's database, so that database is kept, even though it holds no app data.
- Integration tests keep their own Neon test branch (`TEST_DATABASE_URL`); they truncate only the command center's tables.

## Consequences

- Both apps see the same rows as soon as the launch app also uses this branch.
- Two schema styles live side by side: UUIDs for the command center, BIGINT identities for launch tables.
- The database is in us-east-2, so the Vercel functions region should be `iad1`.
