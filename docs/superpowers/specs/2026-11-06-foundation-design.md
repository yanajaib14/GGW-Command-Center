# GGW Command Center — Foundation (Version 1) Design

- **Date:** 2026-11-06
- **Status:** Draft for owner review
- **Scope:** Phase 0 foundation only. No restaurant workflows, no AI.

## 1. Context

GGW Command Center is a mobile-first operations platform for Glai Gung Won, a
Thai-inspired restaurant in Arizona. It replaces the earlier launch dashboard
(`New-Restaurant--main`), which was audited on 22 Oct 2026 and found to have no
real sign-in (every visitor was treated as Owner) and an unreachable database.

This is a fresh build. No data is migrated from the old app.

Opening is 6 to 12 weeks away. The foundation must be finished early enough
that daily routines (checklists, food-safety logs, compliance calendar) can be
built on it before doors open.

## 2. Goals

1. Staff sign in with their own account. Only invited people can join.
2. Each person holds one or more roles at one or more locations. The server
   enforces permissions on every protected page and action.
3. Three experiences exist as shells: Employee Hub, Manager Workspace, Owner
   Dashboard.
4. The data model carries organization and location identifiers, so a second
   location or AI agents can be added without restructuring.
5. Important changes are recorded in an append-only audit log.
6. A reusable, kitchen-proof design system and responsive app shell.
7. Strict type checking, linting and automated tests run on every change.

## 3. Non-goals for Version 1

- Any AI functionality.
- Restaurant workflows: checklists, temperature logs, prep, inventory,
  purchasing, scheduling, reservations, maintenance, financial reports.
- Offline data entry (only offline detection and a banner).
- HR-sensitive fields (pay, home address, emergency contacts, documents).
- Multi-factor authentication (not available on Neon Managed Auth yet).
- Migrating data from the old launch dashboard.

## 4. Product principles

These carry forward from the audit and the owner's brief:

- **Buy the transaction systems, build the glue.** POS, scheduling,
  payroll and accounting are future integrations, not rebuilds. The roadmap
  marks them "connect".
- **Kitchen-proof.** Phone first, large tap targets, readable at arm's length,
  clear behaviour when Wi-Fi drops.
- **Authentication is not authorization.** Signing in proves identity; the
  server decides what a person may do, every time.
- **Every critical workflow works without AI.** AI agents, when added, call the
  same permission-checked business functions as people do.
- **Boring, well-supported technology.** Few dependencies, each with a reason.
- **No destructive data changes without owner approval.** Records are marked
  inactive, never deleted.

## 5. Technology

| Concern | Choice | Why |
|---|---|---|
| Framework | Next.js (App Router), TypeScript strict | Native to Vercel; server components and server actions keep logic server-side. |
| Styling | Tailwind CSS with design tokens | Tokens in one place; consistent components. |
| Database | Neon Postgres | Owner's chosen provider. |
| Data access and migrations | Drizzle ORM + drizzle-kit | Typed queries, versioned SQL migrations, light footprint. |
| Identity | Neon Auth (Managed Better Auth) via `@neon/auth` | Generally available; users and sessions live in the same database (`neon_auth` schema). |
| Unit and integration tests | Vitest | Fast; tests business rules without a browser. |
| End-to-end tests | Playwright | Sign-in and access checks in a real browser. |
| Hosting and CI | Vercel; GitHub Actions for checks | Repository is already connected to Vercel. |

Package versions are pinned when the project is initialized; the
implementation plan records the exact Neon Auth setup steps verified against
current Neon documentation at that time.

## 6. Identity and authorization approach

**Decision (Option A):** Neon Auth handles identity only. The application owns
roles, permissions, invitations and the audit log in its own tables.

Rejected alternatives:

- *Self-managed Better Auth on Vercel* — gains MFA today but adds ongoing
  maintenance of the auth server and email delivery. Can be adopted later
  without changing the application's permission tables.
- *Neon Auth Organization plugin for roles* — beta, fixed owner/admin/member
  roles, no custom permissions or per-location roles.

Sign-in method: email one-time code (Neon Auth Email OTP). Magic link may be
enabled later. Getting started uses Neon's shared mail sender; production
requires the owner's own SMTP sender before real staff are invited.

## 7. Data model

All application tables live in the `public` schema. Neon Auth owns the
`neon_auth` schema; the application only reads its user ID.

### Conventions

- Primary keys are UUIDs generated by the database.
- Every table has `created_at` and `updated_at` (`timestamptz`, UTC).
- Every table has `organization_id`. Tables whose rows belong to one
  restaurant also have `location_id`.
- No hard deletes. Status fields or `revoked_at` / `ended_at` timestamps mark
  records inactive.
- Schema changes are numbered Drizzle migrations committed to Git. Migrations
  that drop or rewrite data require explicit owner approval.

### Tables

**organizations**
`id`, `name`, `slug` (unique), timestamps.

**locations**
`id`, `organization_id`, `name`, `address`, `timezone` (IANA, default
`America/Phoenix`), `status` (`active` | `closed`), timestamps.

**employees**
`id`, `organization_id`, `auth_user_id` (nullable, unique; Neon Auth user ID,
set when the invitation is accepted), `first_name`, `last_name`,
`display_name`, `email` (work email, unique per organization, stored
lower-case), `phone` (nullable), `status` (`invited` | `active` | `suspended`
| `left`), timestamps.

**roles**
`id`, `organization_id`, `key` (unique per organization, e.g. `owner`),
`name`, `description`, `is_system` (system roles cannot be deleted or
renamed), timestamps.

**role_permissions**
`role_id`, `permission` (text; must be a key in the code permission catalog),
`organization_id`, `created_at`. Primary key (`role_id`, `permission`).

**role_assignments**
`id`, `organization_id`, `employee_id`, `role_id`, `location_id` (nullable;
null means all locations in the organization), `granted_by_employee_id`,
`granted_at`, `revoked_at` (nullable), `revoked_by_employee_id` (nullable).
An assignment is active when `revoked_at` is null. At most one active
assignment per (`employee_id`, `role_id`, `location_id`).

**invitations**
`id`, `organization_id`, `employee_id` (the `invited` employee row created
with the invitation), `email`, `location_id`, `role_id`, `token_hash`
(SHA-256 of a random 32-byte token; the raw token appears only in the email
link), `invited_by_employee_id`, `expires_at` (7 days after creation),
`accepted_at`, `revoked_at`, timestamps.

**audit_log**
`id`, `organization_id`, `location_id` (nullable), `actor_employee_id`
(nullable for system actions such as setup), `action` (e.g.
`invitation.created`), `entity_type`, `entity_id`, `before` (jsonb, nullable),
`after` (jsonb, nullable), `created_at`. The application database role has
INSERT and SELECT only on this table; UPDATE and DELETE are revoked.

### Deliberately absent

HR-sensitive data will live in a separate table with its own permissions when
HR features arrive, never as extra columns on `employees`.

## 8. Permissions

### Catalog

Permissions are defined once in code (`src/server/auth/permissions.ts`) as a
typed list. The database stores which roles hold which permissions.

| Permission | Owner | Manager | Employee |
|---|:-:|:-:|:-:|
| `dashboard.employee` | ✓ | ✓ | ✓ |
| `dashboard.manager` | ✓ | ✓ | |
| `dashboard.owner` | ✓ | | |
| `profile.edit_own` | ✓ | ✓ | ✓ |
| `staff.view` | ✓ | ✓ | |
| `staff.invite` | ✓ | ✓ | |
| `staff.manage` | ✓ | | |
| `roles.manage` | ✓ | | |
| `locations.manage` | ✓ | | |
| `audit.view` | ✓ | | |

### Enforcement

- One server function, `requirePermission(permission, { locationId })`, is the
  only gate. It:
  1. reads the Neon Auth session on the server;
  2. loads the employee by `auth_user_id`;
  3. rejects if no employee, or status is not `active`;
  4. collects permissions from active role assignments that apply to the
     location (exact match or organization-wide);
  5. returns the actor context (employee, organization, allowed locations)
     or throws a typed `Forbidden` / `Unauthenticated` error.
- Every protected page, server action and route handler calls it before doing
  anything else. A lint rule or test asserts that every server action file
  imports it.
- Data-access functions take the actor context and always filter by
  `organization_id` and the actor's allowed locations.
- Status and role changes take effect on the next request; there is no cached
  permission set that outlives a request.

### Guardrails

- **No escalation:** an actor can only grant a role whose permissions are all
  held by the actor. Managers can therefore invite Employees only.
- **Last Owner:** the last active, organization-wide Owner cannot be revoked,
  suspended or marked as left.
- **No self-change:** an actor cannot change their own role assignments or
  status.
- **Audit:** invitation created, accepted, revoked or expired-on-use; role
  granted or revoked; employee status changed; role permissions changed;
  location created or changed; setup run. Each writes an audit entry in the
  same database transaction as the change.

## 9. Invitations and onboarding

1. A user with `staff.invite` submits name, email, location and role.
2. The server checks the no-escalation rule, creates the `invited` employee row
   and the invitation, writes the audit entry, and emails a link containing the
   raw token.
3. The invitee opens the link and signs in with an email one-time code.
4. The server verifies: token hash matches, invitation not expired, revoked or
   accepted, and the signed-in email equals the invitation email
   (case-insensitive). On success it sets `employees.auth_user_id`, sets status
   `active`, creates the role assignment, marks the invitation accepted, and
   writes audit entries, all in one transaction.
5. Any signed-in user with no active employee record sees the **No access**
   screen and can reach no data.

Re-inviting an email revokes its previous open invitation. Invitations are
single-use.

### First Owner bootstrap

A one-time command (`npm run setup:owner`) reads the organization name,
location name and owner email from command-line arguments. In one transaction
it creates the organization, the location, the three system roles with the
permission matrix above, and the owner's invitation (organization-wide Owner
role). It prints the invite link to the terminal. It refuses to run if any
active Owner already exists.

## 10. Experiences, screens and app shell

### Shell

- Phone: bottom tab bar. Tablet and desktop (≥ 768 px): left sidebar.
- Experience switcher shown only to people with more than one experience.
- Navigation lists only destinations the person is permitted to open.
- Offline banner using the browser online/offline events; installable as a
  web app (manifest and service worker for the shell only).
- Light and dark themes from the same tokens, meeting WCAG AA contrast.

### Screens

| Route | Permission | Content |
|---|---|---|
| `/sign-in` | public | Email entry, code entry, error and loading states. |
| `/invite/[token]` | public, then signed in | Invitation summary, sign-in, acceptance result. |
| `/no-access` | signed in | Explanation and sign-out. |
| `/hub` | `dashboard.employee` | Greeting, location, placeholder "Today" cards, link to profile. |
| `/hub/profile` | `profile.edit_own` | Edit display name and phone. |
| `/manager` | `dashboard.manager` | Staff list (`staff.view`), invite form (`staff.invite`), pending invitations with revoke. |
| `/owner` | `dashboard.owner` | Staff overview, employee detail with role and status changes (`staff.manage`), roles and permissions (`roles.manage`), locations (`locations.manage`), audit log (`audit.view`), empty report placeholders. |

After sign-in, people land on the highest experience they hold (Owner, then
Manager, then Employee).

### Design system

Built once in `src/components/ui` and reused everywhere: Button, Input, Field
(label, hint, error), Select, Card, ListRow, Badge, EmptyState, PageHeader,
Banner, Dialog, Toast. Tokens (colour, spacing, radius, type scale, touch
target minimum 48 px) live in the Tailwind theme. New screens compose these;
new primitives are added only when no existing one fits.

## 11. Project structure

```
src/app/            routes and layouts only; no business logic
src/components/ui/  design-system primitives
src/components/shell/  app shell, navigation, experience switcher
src/features/<area>/   business logic per area (staff, invitations, roles,
                       locations, audit): server actions, queries, validation
src/server/auth/    session reading, permission catalog, requirePermission
src/server/db/      Drizzle client and transaction helper
src/server/audit/   audit-log writer
src/db/schema/      Drizzle table definitions
src/db/migrations/  generated, numbered SQL migrations
scripts/            setup:owner and other one-off commands
tests/unit/         permission and guardrail tests
tests/integration/  database-backed tests against a Neon test branch
tests/e2e/          Playwright sign-in and access tests
docs/               architecture.md, permissions.md, decisions/
CLAUDE.md           instructions for Claude Code
AGENTS.md           points other agents to CLAUDE.md
```

Business rules live in `src/features` and `src/server`, so future AI agents can
call the same functions under their own permission-checked identity.

## 12. Testing and checks

- **Unit:** every cell of the permission matrix; each guardrail (no escalation,
  last Owner, no self-change, suspended and left employees, location
  isolation).
- **Integration:** invitation lifecycle (create, accept, wrong email, expired,
  revoked, reused); setup command refusal when an Owner exists; audit entries
  written with each change; audit log rejects UPDATE and DELETE. Runs against a
  dedicated Neon test branch, never production.
- **End-to-end:** sign-in page loads; signed-out visitors are redirected from
  protected routes; an Employee cannot open `/manager` or `/owner`.
- **Checks on every pull request (GitHub Actions):** `tsc --noEmit` (strict),
  ESLint, Vitest. Playwright runs against the Vercel preview deployment.

## 13. Documentation

Created in the foundation and kept current:

- `CLAUDE.md` — conventions, commands, security rules, "never" list.
- `AGENTS.md` — one line pointing to `CLAUDE.md`.
- `docs/architecture.md` — system overview and the roadmap section.
- `docs/permissions.md` — the catalog, matrix and guardrails.
- `docs/decisions/` — one short record per decision; the first records Option A,
  Drizzle, and email one-time code sign-in.

The database is documented by the Drizzle schema files themselves.

## 14. Configuration and owner setup actions

Secrets are never pasted into chat or committed. `.env.example` lists variable
names only; `.env.local` is ignored by Git.

Expected variables (exact names confirmed against Neon documentation during
implementation): `DATABASE_URL`, `NEON_AUTH_BASE_URL`, and any Neon Auth secret
it requires. Test runs use a separate `DATABASE_URL` for the test branch.

Owner actions, each guided step by step when reached:

1. Enable Neon Auth on the Neon project (confirm the project is in an AWS
   region and has no IP Allow or Private Networking).
2. Enable Email OTP sign-in.
3. Add the Vercel production and preview origins to Neon Auth trusted domains.
4. Add the environment variables in Vercel and in local `.env.local`.
5. Create a Neon branch for automated tests.
6. Before inviting real staff: configure a custom SMTP sender in Neon Auth.

## 15. Roadmap after the foundation

Timed against the opening date, from the 22 Oct audit, adjusted:

- **Phase 1, before opening:** opening and closing checklists, food-safety
  temperature logs, compliance calendar with expiry alerts, recipe costing,
  order guides with par levels, training sign-off.
- **Phase 2, around opening:** role-based Today screens; POS connection
  (connect); daily flash report; manager shift log, waste and incident logs.
- **Phase 3, months 2–6:** inventory counts and actual-vs-theoretical food
  cost, prime-cost report, menu engineering, scheduling app connection
  (connect), QuickBooks sync (connect), review monitoring.
- **Later:** AI management agents (read-only first, people approve actions),
  catering, loyalty, additional locations.

## 16. Risks and open items

- **No MFA on Owner accounts.** Mitigation: email one-time codes (no
  reusable password), audit log of every sensitive change, and the option to
  sign out all sessions; revisit when Neon ships MFA, or move to self-managed
  Better Auth.
- **Shared mail sender limits.** Must switch to custom SMTP before staff
  onboarding; tracked as owner action 6.
- **Neon Auth API drift.** The implementation plan re-verifies setup steps
  against current Neon docs before writing auth code.

## 17. Done when

- The owner signs in via the setup invitation and reaches the Owner Dashboard.
- The owner invites a Manager; the Manager invites an Employee; each lands on
  the correct experience and cannot open the others' screens.
- An uninvited email that signs in sees only the No access screen.
- Suspending an employee blocks them on their next request.
- Every change above appears in the audit log.
- All checks pass in CI, and the app is deployed on Vercel.
